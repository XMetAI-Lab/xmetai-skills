# 降水个例分析报告骨架

覆盖 `weather_ts_det` 流程下的**暴雨过程个例检验**（`configs/rainstorm_ts_single_*`），
渲染器是 `scripts/reporting/reports/rainstorm_report.py`，入口是
`scripts/render_rainstorm_report.py`。

**与其他骨架不是一个家族**：那些吃的是**一次连续时段评测**的宽表，
按"时效 / 等级"分节；这一份吃的是一整年 **43 个过程 × 2 种口径**，
每个过程一段独立产物，所以**按"过程"分节**。同样的 `weather_ts_det` 流水线，
产物形状不同，走的渲染器也不同（`ts_report.py` 喂不进来，见 SKILL.md 能力路由表）。

**照这个填空就是最终报告。** `{…}` 是占位符，**其余每一个字逐字照抄，不许改**——
包括标点、加粗、`>` 引用块、表头与分隔行、图注与表题的位置。

报告按**论文实验章节**写：每一节都是「引导句 → 图表 → 小结」。
**图注在图下方、表题在表上方**（中文论文的排版惯例），图和表按在报告里出现的顺序
连续编号（`图 1`…`图 N`、`表 1`…`表 N`），**第三节的重复块之间也连续编号，不重置**。

> **第三节的「过程块」是可重复的**：给 `--process` 几个编号就重复几次，
> 每次的 `3.x` 号依次递增（`3.1`、`3.2`…），里面的表号、图号跟着全篇往下走。
> 下面的骨架只写了一个块，`{x}` 是占位符，**不要照抄成固定的 `3.1`**。

**两种口径互不可比**，报告里两套数分节呈现，只在同一口径内跨模型、跨过程比：
口径 A（逐日 24h）一天一个 08–08 窗、基准率随每日实况浮动；
口径 B（过程累积）一根预报累加整段、基准率显著更高。同一个过程的 TS 在两者之间
可以差好几倍，跨口径比大小没有意义——报告第二、三、四节都按这个前提写。

**本骨架不出降水空间分布**。评测产物里只有站点列联表的聚合统计
（hits / misses / false_alarms / n_pairs / TS…），没有逐站或逐格降水量，
画不出实况场、也画不出预报−实况差值场。第六节第 8 条把这条写明了，
**不要因为"别的降水报告都有落区图"就补一张**。

**四个位置固定不动**，少了任何一个都算骨架被改坏：

1. 抬头三行（**主模型** / **过程编目** / **归档文件**）与那一段 `>` 口径提醒；
2. 第二节**两张**全 43 行的挑选依据宽表（口径 A、口径 B 各一张）
   与紧随其后的**两张全 43 过程的柱状图**（口径 A、口径 B 各一张，
   A 在前），以及它们的表题、图注；
3. 第三节每个过程块的**四个小节**（过程概况 / 口径 A / 口径 B / 过程小结），
   每节末尾的 `**小结**` 必须带数字；
4. 第六节**十条**口径与注意事项，末尾一条 `>` 数据来源。

> `assets/templates/` 是格式契约，**不参与渲染**——渲染器把正文写死在
> `rainstorm_report.py` 里，这份骨架靠人工与它逐字对齐。`tests/` 里只有
> 真实数据集成测试（`tests/integration/test_rainstorm_ts_realdata.py`），
> **没有骨架文字对照测试**；改渲染器的静态文字时，**这份骨架要一起改**。

**两种口径怎么算**

## 六、口径与注意事项

1. **两种口径互不可比**。口径 A 的窗只有 24h，实况达到阈值的站点占比低、基准率也低；口径 B 把整段累加成一个总量，基准率高得多。同一个过程的 TS 在两者之间可以差好几倍；跨口径比大小没有意义，只在本口径内比。
2. **口径 A 的过程值是把起报日的四格表汇总后重算**，不是逐日 TS 的算术平均。TS 是比率，简单平均会给「只报出十几个站、TS 恰好为 0」的起报日与事件上千的起报日**同样的权重**，把均值拖偏；汇总重算等价于把该过程全部「站点·日」样本当成一个整体，小样本日自然只占很小的权重。注意口径 A 汇总的仍是**逐日 24h 窗**的样本，与口径 B 那根累积窗不是同一个量，两者照样不可比。
3. **跨模型汇总只比同一批过程**。某个模型缺段时，各算各的均值就是不同的分母，相减得到的 Δ 里混着覆盖率差、不是模型差异；第四节的汇总表因此**逐行只取所有模型都有有效值的过程**，各模型的过程数一定相等（表题给出这个数，会小于 43）。注意「有产物」和「有有效值」是两回事：一段过程可能整个 `_total` 缺、可能该档无事件，两种都会让某个模型少一个数。
4. **差值小于 0.005 一律视为并列**，报告里的「领先 / 落后」都不含这一区间；胜负数因此可能加起来小于过程总数。
5. **「缺」与「—」不是一回事**：「缺」是该段产物整个不在（多半是那几天的预报或观测数据缺），「—」是有产物但该档无有效 TS（无事件或无有效配对）。两者都不补 0。
6. **高等级档的样本量急剧收缩**。≥100mm 尤其是 ≥250mm 档在很多过程上根本没有事件，TS 为空是「无事件」而不是「技巧为 0」；这些档的差异不作结论。
7. **指标不重估，只汇总**。逐日值、口径 B 的值都直接来自产物里的 `diagnostics/categorical_wide.csv`，一个字没动；口径 A 的过程级数值是把同一份产物里的 hits / misses / false_alarms 按起报日**加总后按定义再算一次**（第 2 条），没有用默认值或估算值补全任何缺格。
8. **本报告不含降水空间分布**。评测产物里只有站点列联表的聚合统计（hits / misses / false_alarms / n_pairs / TS…），没有逐站或逐格的降水量，画不出实况场、也画不出预报−实况差值场。要看落区得回头读原始预报 nc 与站点报文（配置里的预报根目录 / 站点根目录），那是另一个脚本。
9. **过程边界用 08–08 日界**，与纪要表的 0–0 日历口径头尾各差 8 小时；口径 B 的窗因此是 (结束日 − 开始日 + 2) 天，比纪要表的自然日数多一天。
10. **202519 与 202520 起止完全相同**（纪要表把同一时段的两个侧面分列两条），各评各的、不合并——本报告里它们各占一行，数字相同属正常。

## 与骨架对不上的地方

以下都是渲染器的**已知取舍**，不是骨架被改坏：

- **抬头没有"报告生成时间"**。其他家族有，这一份故意不给——报告的每个数字都能
  从产物重放出来，加时间戳会让同一批产物出不了逐字节相同的报告，骨架也就没法
  当格式契约用了。
- **第三节的表号、图号跨过程块连续**（`表 3`、`表 5`…），不按过程块重置。
  骨架里写的是 `表 {N}`，不是 `表 1`。
- **第二节的 Δ 列在表头里重复三次**（每个阈值段一次），且三次文字完全相同。
  这是 `_screening_header` 的既有形态，与 `render_rainstorm_summary.py` 的
  `screening.md` 一致，不要"优化"成只出现一次。
- **模型多于两个时，Δ / 胜负计数 / 改进建议仍只针对主模型与第一个对比模型**。
  各模型的数值和柱状图里的全部模型都照常输出，但 `_delta_cell`、`_win_counts`、
  `_advice_section` 只取 `names[0]` / `names[1]`，所以表里只有一列 Δ、小结里只有
  一组胜负计数。要做两两矩阵就拆成多份报告（每次把不同的模型放在第二个位置），
  不要手工补列。
- **口径 B 的等级表带 ≥0.1 一行**。0.1mm 是"有降水"档，属于配置里的
  `TS_THRESHOLDS`，不是错误。
